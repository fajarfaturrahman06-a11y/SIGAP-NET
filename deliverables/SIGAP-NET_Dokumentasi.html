1. Deskripsi dan Tujuan SIGAP-NET

SIGAP-NET (Sistem Integritas Konfigurasi dan Respons Gangguan Jaringan) adalah aplikasi web berbasis Flask untuk mengelola backup konfigurasi router MikroTik sekaligus memantau integritas konfigurasi tersebut terhadap baseline yang ditetapkan. Nama resmi aplikasi dan variannya didefinisikan di config.py (APP_NAME = 'SIGAP-NET', APP_VERSION = '1.0.0').

1.1 Tujuan

  1. Tersedianya backup konfigurasi terpusat — konfigurasi tiap router tersimpan sebagai file dan tercatat di database, bukan terserak di lokal admin.
  2. Deteksi perubahan tidak sah (drift) — setiap konfigurasi diperiksa terhadap baseline aktif menggunakan hash SHA-256 semantik dan diff berjenjang risiko.
  3. Respons gangguan yang terkontrol — perubahan berisiko tinggi memicu insiden, dan pemulihan konfigurasi wajib melewati alur permintaan → persetujuan → eksekusi.
  4. Jejak audit yang dapat dipertanggungjawabkan — seluruh aksi penting tercatat pada audit trail yang bersifat append-only (tidak bisa diubah/dihapus).
  5. Pembatasan akses berbasis peran — pemisahan hak antara admin, operator, dan auditor agar tanggung jawab terpisah (segregation of duties).

1.2 Cakupan penggunaan

Dirancang untuk lingkungan laboratorium jaringan dan pendidikan (UKM Kartika Cyber, POLTEKAD), termasuk kebutuhan demonstrasi kompetisi keamanan siber defensif. Komunikasi SSH ke perangkat MikroTik dilakukan melalui paramiko dengan kebijakan RejectPolicy — koneksi ditolak bila sidik jari host belum dikenal.

4.1 Alur deteksi gangguan (inti SIGAP-NET)

  1. Konfigurasi perangkat diperoleh (mode simulasi dari lab_config, atau via SSH untuk perangkat nyata).
  2. services/integrity.py mem-parse konfigurasi lalu menghitung hash SHA-256 semantik yang stabil terhadap spasi, kutip, dan urutan baris tertentu.
  3. Konfigurasi dibandingkan dengan baseline aktif → daftar perubahan (config_changes).
  4. services/risk.py menilai tiap perubahan (mis. firewall dimatikan → HIGH) → status check OK / CHANGED / DRIFT.
  5. Bila risiko memenuhi syarat, services/monitoring.py membuat/memperbarui insiden (insiden terbuka serupa digunakan ulang, tidak duplikat).
  6. Operator mengajukan respons pemulihan; penyetujuan dan eksekusi dicatat; services/audit.py menyimpan jejaknya secara permanen.

6. Instalasi dan Konfigurasi

6.1 Prasyarat

  • Python 3.12 atau lebih baru (audit lingkungan: Python 3.13.7).
  • MySQL 8.0 bila tidak memakai SQLite default.
  • Docker & Docker Compose (opsional, untuk deployment terkontainerisasi).

6.2 Instalasi lokal (development)

cp .env-example .env
python -m venv .venv
.venv\Scripts\activate            # Windows
pip install --upgrade pip
pip install -r requirements.txt

set FLASK_APP=app.py              # PowerShell: $env:FLASK_APP="app.py"
set FLASK_ENV=development

flask init-db                     # inisialisasi skema database
flask create-admin admin          # password diminta interaktif (tidak dari argumen)
Aturan password: minimal 12 karakter, wajib huruf besar + huruf kecil + angka + simbol, tidak boleh berisi nama pengguna, dan tidak boleh termasuk daftar password umum (security.py:176). Password diminta tersembunyi (hide input) sehingga tidak masuk riwayat shell. Tidak ada akun default — aplikasi tidak membuat akun otomatis.

6.3 Menjalankan aplikasi

# Development
flask run --host=0.0.0.0 --port=5000
# akses: http://localhost:5000

# Docker Compose (bila Docker tersedia)
docker compose up -d --build
# akses: http://localhost:5000 atau http://localhost:8500

7.2 Alur demonstrasi standar (mode simulasi, aman)

  1. Login menggunakan akun yang dibuat sendiri melalui flask create-admin.
  2. Buka Dashboard — amati statistik integritas dan aktivitas.
  3. Siapkan data demo — perangkat EDGE-RTR-01 (IP 10.10.10.1, adapter simulation) dan baseline lab dibuat oleh services/demo_data.py (via flask seed-demo atau saat skenario dijalankan).
  4. Jalankan Skenario 1 — Perubahan Normal: catatan perangkat berubah → hasil check CHANGED, risiko LOW, tidak ada insiden.
  5. Jalankan Skenario 2 — Perubahan Mencurigakan: firewall dinonaktifkan → risiko HIGH, insiden baru dibuat otomatis.
  6. Jalankan Skenario 3 — Perubahan Akses: SSH diaktifkan → risiko HIGH, insiden dibuat, lalu operator mengajukan pemulihan.
  7. Alur respons: Ajukan restore → setujui (oleh berwenang; persetujuan diri untuk risiko tinggi diblokir) → eksekusi → verifikasi status insiden selesai.
  8. Periksa Audit — seluruh langkah di atas tercatat lengkap dengan aktor, peran, IP, waktu, dan hasil.
  9. Reset data demo bila perlu (Settings → reset simulasi): data baseline/check/insiden demo dibersihkan, audit trail tetap tersimpan.

7.3 Menambahkan router nyata (opsional, untuk lingkungan lab)

  1. Tambahkan router melalui menu Routers (host, port, kredensial SSH).
  2. Daftarkan sidik jari host perangkat: ssh-keyscan -p 22 <ip> >> ~/.ssh/known_hosts lalu set SSH_KNOWN_HOSTS_FILE. Tanpa ini, koneksi SSH akan ditolak (kebijakan RejectPolicy).
  3. Uji koneksi, lalu jalankan backup. File backup tersimpan pada direktori backups/.

9. Batasan Sistem

Bagian ini disusun dari hasil audit kode dan catatan handoff — penting untuk transparansi demonstrasi kompetisi.
  1. Restore perangkat nyata belum diimplementasikan. Flag SIGAP_ALLOW_REAL_RESTORE dinonaktifkan secara default dan jalurnya tetap diblokir; yang tersedia hanya restore simulasi.
  2. Tanpa akun default. Tidak ada admin/operator/auditor bawaan; akun harus dibuat lewat CLI eksplisit.
  3. Database default SQLite. MySQL didukung via DATABASE_URL tetapi butuh konfigurasi terpisah.
  4. Regresi statistik dashboard (dicatat di HANDOFF.md dan terverifikasi di kode):
    • Device.latest_check dihapus dari model tetapi masih dipanggil templates/device_detail.html:30 → kolom "Snapshot Terakhir" selalu menampilkan —.
    • Device.integrity_state hanya mengembalikan UNKNOWN / INTACT / DRIFT, sedangkan app.py:393 masih menghitung nilai NOT_CHECKED → statistik "belum diperiksa" selalu 0 dan UNKNOWN tidak memiliki pemetaan warna.
  5. test_dashboard.py di root repo menulis ke database utama (tanpa override DATABASE_URL) — jangan dijalankan; gunakan python -m pytest tests -q yang mengarah ke database sementara.
  6. Tabel devices mengandung baris uji (test-*) dari pemeriksaan sebelumnya — sebaiknya dibersihkan sebelum demonstrasi publik.
  7. Belum ada ekspor laporan PDF bawaan dalam aplikasi; ekspor dilakukan melalui fitur unduhan snapshot/baseline/backup.
  8. Deployment produksi Linux mengasumsikan systemd + Gunicorn; lingkungan Windows hanya untuk development.
  9. Mode scheduler dapat dimatikan dengan SCHEDULER_ENABLED=false; berjalan sebagai proses background dengan mekanisme leadership lock.
